# 산출물 양식

모든 산출물의 둘째 줄에 작성자, 상태(`draft` 또는 `approved`), 앞 단계 산출물과 그 승인 날짜를 적는다.

## docs/<branch_name>/intent.md

```
# Intent: <한 줄 이름>
Author: <이름 (역할)>. Status: draft.

## Problem
지금 무엇이 안 되는가. 사용자의 말은 인용으로 남긴다.

## Proposed outcome
바뀐 뒤 무엇이 가능해지는가. 해결 방법이 아니라 결과를 적는다.

**성공 기준:** 측정할 수 있는 조건과 그것을 어디서 확인하는지.

## Affected users and systems
누가 쓰는가. 어떤 화면, 인터페이스(API, CLI), 서버, 외부 서비스가 바뀌는가.

## Constraints
빼면 안 되는 기능, 승인 없이 하면 안 되는 일, 범위 밖인 것.

## Open questions
아직 정하지 못한 것. 없으면 "없음"이라고 적는다.
```

## docs/specs/<spec_name>.md

`<spec_name>`은 영역 이름이다(예: `backend`, `frontend`, `scalability`). 이미 있는 영역 spec을 고칠 때는 둘째 줄의 `Status`와 `Intent`를 이번 주기 것으로 바꾸고, 요구사항과 결정 사항은 지우지 않고 이어서 적는다.

```
# Spec: <영역 이름>
Author: <이름>. Status: draft. Intent: `docs/<branch_name>/intent.md` (approved <날짜>).
Mockup: <링크 또는 "없음">

## 우려 사항
사용자가 결정해야 하는 것. 결정되면 아래로 옮긴다.

## 결정 사항
<날짜> 사용자가 승인한 결정.

## 현재 상태
코드에서 확인한 사실. 파일 이름과 함께 적는다.

## 요구사항
| ID | 요구사항 | 확인 방법 |
|---|---|---|
| R1 | | |

## 화면과 인터페이스
목업의 화면 이름과 상태(비어 있음, 진행 중, 오류). 화면이 없는 변경은 입력과 출력의 예시.

## 범위 밖
이번에 하지 않는 것.
```

## docs/<branch_name>/plan.md

```
# Plan: <이름>
Author: <이름>. Status: draft. Spec: `docs/specs/<spec_name>.md` (approved <날짜>). Intent: `docs/<branch_name>/intent.md`.

## 확인이 필요한 우려 사항
1. **<제목>.** 무엇이 문제인가.
   - 제안: <권하는 선택>
<날짜> 사용자 결정: <승인된 뒤에 적는다>

## 구현 단계
### 1. <단계 이름> (R 번호)
- 바꾸는 것
- 테스트: 무엇을 어떤 테스트로 확인하는가

## 바뀌는 파일

## 리스크
- **<리스크>:** 영향과 대비. 버린 대안이 있으면 이유와 함께 적는다.

## 되돌리는 방법
배포한 뒤 문제가 생기면 실행할 명령. 되돌릴 수 없는 변경은 따로 표시한다.

## 성공 기준
- spec의 요구사항 확인 방법을 모두 통과한다.
- 테스트 종류별 통과 조건과 커버리지.
- 남길 증거(스크린샷, 영상, 명령 출력)와 그 위치.
- 배포 뒤 intent의 성공 기준을 확인하는 방법.
```

## docs/STATUS.md

```
# Status

단계: **<단계>** (<날짜>부터)

## 배포된 것
버전과 빌드, 적용한 마이그레이션, 배포한 서비스, 등록한 설정.

## 배포 전 확인
테스트 수와 결과, 커버리지, 모델 평가 결과(해당하면), 남긴 증거.

## 실제 환경에서 확인할 것

## 알려진 문제
재현 방법이나 빈도와 함께 적는다.

## 성공 기준
intent의 성공 기준과 지금까지의 결과.

## 이번 주기
걸린 시간, 승인 뒤 spec·plan을 고친 횟수, 테스트가 처음에 통과했는지.
```
