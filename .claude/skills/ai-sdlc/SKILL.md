# AI-native SDLC

각 단계는 산출물 하나를 커밋하면서 끝나고, 다음 단계는 그 산출물을 읽으면서 시작한다. 커밋 기록이 곧 결정의 기록이다. 판단이 필요한 결정은 모두 사용자가 내린다.

| 단계 | 읽는 것 | 남기는 것 | 사용자가 결정하는 것 |
|---|---|---|---|
| Plan | 사용자와의 인터뷰, `docs/STATUS.md` | `docs/<branch_name>/intent.md` | 의도가 맞는지 |
| Design | `intent.md`, 디자인 가이드 | `docs/specs/<spec_name>.md`, 목업 | 요구사항과 디자인 |
| Build | `intent.md`, `spec.md`, 코드 | `docs/<branch_name>/plan.md`, 코드와 테스트 | 계획과 우려 사항 |
| Test | `plan.md`의 성공 기준 | 테스트 출력 | 없음. 결과를 보고받는다 |
| Deploy | 변경 내용, 검토 결과 | 머지, 릴리스 | 운영에 닿는 모든 실행 |
| Maintain | 운영 로그, 사용 기록 | `docs/STATUS.md`, 다음 `intent.md` | 지금 고칠지, 미룰지, 닫을지 |

아래에서 `intent.md`, `spec.md`, `plan.md`는 위 표의 경로에 있는 파일을 가리킨다. 산출물 양식은 `templates.md`에 있다.

이 문서는 절차만 정한다. 테스트, 빌드, 배포, 평가에 쓰는 실제 명령은 프로젝트의 `AGENTS.md`나 `CLAUDE.md`, README에서 찾는다. 거기에도 없으면 추측하지 말고 사용자에게 묻는다.

## 공통 규칙

- **단계를 건너뛰지 마시오.** 앞 단계 산출물의 `Status`가 `approved`가 아니면 다음 단계를 시작하지 않는다. 작은 수정은 아래 "작은 변경"을 따른다.
- **산출물마다 원본은 하나다.** 의도는 `intent.md`, 요구사항은 `spec.md`, 구현 범위는 `plan.md`, 지금 상태는 `STATUS.md`에만 적는다. 다른 문서에는 다시 쓰지 말고 파일을 가리킨다.
- **뒤 단계에서 앞 산출물이 틀렸음을 알게 되면 그 산출물을 먼저 고치시오.** 코드만 고치고 문서를 두면 다음 주기가 틀린 문서에서 시작한다. 바꾼 이유를 한 줄 남기고, 승인된 내용이 달라지면 다시 승인받는다.
- **새 주기를 시작할 때** 이전 `intent.md`, `plan.md`를 `docs/archive/<이름>-<YYYY-MM-DD>.md`로 옮긴다. 영역 spec은 옮기지 않고 그 자리에서 계속 고친다.
- **사용자가 말하지 않은 것을 사실로 적지 마시오.** 추측은 `Open questions`나 우려 사항에 질문으로 적는다.
- **승인은 그 단계와 그 대상에만 유효하다.** 계획 승인이 운영 DB 변경이나 릴리스 배포의 승인은 아니다.

## Plan

`docs/<branch_name>/intent.md`를 작성하시오. 무엇을 왜 바꾸는지, 성공을 어떻게 알아볼지 정하는 단계다. 해결 방법은 아직 정하지 않는다.

0. branch를 만든다. 유저에게 워크트리를 만들 것이냐고 질문한다. (워크트리는 `~/.worktrees/<project_name>/<branch>`에 만든다)
1. `docs/STATUS.md`의 알려진 문제와 이전 주기의 성공 기준 결과를 먼저 읽는다. 파일이 없으면 첫 주기이므로 넘어간다.
2. 사용자를 인터뷰한다. 문제, 대상 사용자, 제약, 성공 기준이 분명해질 때까지 묻는다. 사용자의 표현은 인용으로 남긴다.
3. `templates.md`의 양식으로 `intent.md`를 쓴다. 성공 기준은 측정할 수 있어야 한다.
4. 사용자가 읽고 고친 뒤 승인하면 `Status: approved`로 바꾸고 커밋한다.

끝나는 조건: `Open questions`가 비었거나, 남은 질문을 사용자가 Design으로 넘기기로 했다.

## Design

`docs/specs/<spec_name>.md`를 작성하시오. 요구사항과 디자인을 한 번에 정한다.

`<spec_name>`은 기능이나 브랜치의 이름이 아니라 **영역**의 이름이다. 예: `backend`, `frontend`, `scalability`. 영역 spec은 주기가 끝나도 남아서 그 영역의 요구사항을 계속 쌓아 간다. 이번 변경이 닿는 영역의 spec이 이미 있으면 그 파일을 고치고, 없으면 새로 만든다. 변경이 여러 영역에 닿으면 영역마다 고친다. 아래에서 `spec.md`는 이번 변경이 닿는 영역 spec 모두를 가리킨다.

1. `intent.md`를 읽는다. `docs/specs/`에 어떤 영역 spec이 있는지 보고, 이번 변경이 닿는 것을 읽는다. 화면이나 문구가 바뀌면 프로젝트의 디자인 가이드(브랜드 스킬, 디자인 시스템 문서, 스타일 가이드)가 있는지 찾아 먼저 읽는다.
2. 코드를 읽어 **현재 상태**를 사실로 적는다. 확인하지 않은 것은 적지 않는다.
3. 요구사항에 ID(R1, R2…)를 붙이고, 각각 **확인 방법**을 적는다. 확인할 방법이 없는 요구사항은 다시 쓴다.
4. 화면이 바뀌면 목업을 만든다. 방향이 갈리면 여러 안을 만들어 고르게 한다. 화면이 없는 변경(API, CLI, 라이브러리)은 목업 대신 입력과 출력의 예시를 적는다.
5. **우려 사항**을 따로 적는다. 서로 어긋나는 요구사항, 디자인 가이드나 기존 기능과 부딪히는 부분, 사용자가 직접 해야 하는 일(계정 설정, 키 발급), 개인정보나 민감한 데이터가 시스템 밖으로 나가는 부분이다.
6. 사용자가 우려 사항을 하나씩 결정하면 `결정 사항`에 날짜와 함께 옮기고, 승인받아 커밋한다.

## Build

`docs/<branch_name>/plan.md`를 작성하시오. **사용자가 승인하기 전에는 코드를 고치지 마시오.** 계획을 쓰는 동안은 코드를 읽기만 한다.

1. `intent.md`, `spec.md`, 관련 코드를 읽는다.
2. `templates.md`의 양식으로 쓴다. 사용자가 확인해야 할 **우려 사항을 가장 위에** 적고, 각각 제안을 붙인다.
3. 바뀌는 파일, 작업 순서, 리스크와 버린 대안, 증명 방법(어떤 테스트, 스크린샷, 영상이 무엇을 증명하는지), 되돌리는 방법을 적는다.
4. 이 대화를 보지 않은 사람이 계획만 읽고 구현할 수 있을 때까지 고친다.
5. 사용자에게는 요약과 결정할 것만 보낸다. 승인받으면 커밋하고 구현을 시작한다.

구현하는 동안:

- 단계마다 브랜치를 나누고, 테스트를 같은 커밋에 넣는다.
- 구현이 계획과 달라지면 **같은 커밋에서** `plan.md`를 고친다. 범위, 리스크, 운영에 닿는 실행이 달라지면 멈추고 다시 승인받는다.
- 병렬 작업은 계획에서 서로 다른 파일만 건드린다고 확인한 작업에만 쓴다. 같은 파일을 건드리면 차례로 한다.
- 비밀값, 생성된 파일, 이미 적용된 마이그레이션은 고치지 않는다. 마이그레이션은 새 파일로 추가한다.

## Test

사용자에게 보이기 전에 스스로 확인하시오. 확인의 증거는 실제 명령 출력이다. "통과했을 것"이라고 쓰지 않는다.

- **버그를 고칠 때:** 실패하는 테스트를 먼저 쓰고, 예상한 이유로 실패하는지 확인한 뒤 고친다. 고치는 동안 그 테스트는 바꾸지 않는다.
- **테스트가 실패하면 코드를 고치시오.** 테스트를 지우거나 느슨하게 만들어 통과시키지 않는다. 테스트가 틀렸다면 이유를 사용자에게 알리고 바꾼다.
- **화면:** 목업과 스크린샷을 나란히 비교하고 다를 때마다 고친다. 보통 두세 번 반복한다.
- **모델 평가:** LLM의 시스템 프롬프트나 도구 정의를 바꾸면 프로젝트의 모델 평가를 다시 돌린다. 실제 호출 비용이 들므로 돌리기 전에 횟수를 알린다. 평가가 없으면 그 사실을 우려 사항으로 알린다.
- **끝난 뒤 한 번 더:** 구현한 맥락을 모르는 하위 에이전트에게 바꾼 흐름과 이웃한 흐름 두 개를 실행해 보고 보고만 하게 한다. 고치는 일은 맡기지 않는다.

## Deploy

운영 직전까지는 준비하고, 운영에 닿는 실행은 사용자가 승인한 뒤에만 하시오.

1. **검토.** 머지하기 전에 `/code-review`로 변경을 검토한다. 코드를 쓴 대화가 스스로 통과시킬 수 없으므로, 검토는 새 맥락에서 한다. 순서는 버그와 논리 오류, 보안(비밀값, 인증, 접근 제어), `spec.md`·`plan.md`와의 일치다. 동작이 깨지거나 데이터가 새는 것만 중요로 분류하고, 사소한 지적은 다섯 개까지만 남긴다.
2. **중요 지적을 고치고** Test의 확인 명령을 다시 돌린다.
3. **사용자에게 보고한다.** 바뀐 것, 테스트 출력, 검토 결과, 남은 위험, 되돌리는 방법을 보낸다.
4. **실행마다 따로 승인받는다.** 기본 브랜치 머지, 운영 DB 마이그레이션, 서버나 함수 배포, secret 등록, 예약 작업 등록, 스토어나 패키지 레지스트리 게시가 해당한다. 실행 전에 대상과 명령을 보여준다.
5. **순서:** 다른 쪽이 의존하는 것을 먼저 배포한다. 보통 DB 마이그레이션, 서버, 클라이언트 순이다. 이미 배포된 예전 클라이언트가 새 서버에서도 동작해야 한다.
6. **되돌리기:** 배포 전에 되돌리는 명령을 `plan.md`에 적어 둔다. 되돌릴 수 없는 변경(열 삭제, 데이터 변환)은 따로 표시하고 승인받는다.
7. **운영 DB 마이그레이션:** 운영 SQL은 스크립트로 준비해 보여주고, 가능하면 트랜잭션으로 실행한다. 실행한 뒤 마이그레이션 이력이 실제 스키마와 맞는지 확인한다. 실행이 막히면 사용자가 `!`로 직접 실행하게 한다.
8. **릴리스:** 버전이나 빌드 번호를 올려 커밋한 뒤 프로젝트의 릴리스 절차대로 빌드하고 올린다. 같은 번호로 다시 올리지 않는다.

## Maintain

`docs/STATUS.md`를 갱신하시오. 배포로 끝나지 않는다. 운영에서 본 것이 다음 주기의 입력이 된다.

1. 배포 직후 `STATUS.md`에 적는다: 단계와 날짜, 배포된 것(버전, 마이그레이션, 서비스, 설정), 배포 전 확인 결과, 실제 환경에서 확인할 것, 알려진 문제, 성공 기준.
2. `intent.md`의 성공 기준을 실제 사용으로 확인한다. 테스트 통과는 성공 기준 달성이 아니다.
3. 문제나 요청이 생기면 **분류**한다.
   - 작고 원인이 분명하다 → "작은 변경"으로 바로 고친다.
   - 여러 곳을 바꾸거나 의도가 달라진다 → 진단을 `intent.md` 양식으로 써서 Plan부터 다시 시작한다.
   - 지금 고치지 않는다 → `STATUS.md`의 알려진 문제에 재현 방법과 함께 남긴다.
   어느 쪽인지는 사용자가 정한다.
4. **운영에서 난 문제는 회귀 테스트로 남긴다.** 모델 동작 문제면 평가 시나리오에 추가한다.
5. **같은 실수가 두 번 나오면 규칙으로 올린다.** 한 번 읽으면 되는 사실은 `AGENTS.md`나 `CLAUDE.md`에, 매번 같은 방식으로 적용해야 하는 절차는 스킬에 적는다. 반드시 지켜져야 하는 것은 hook으로 강제하자고 사용자에게 제안한다.
6. 주기가 끝나면 걸린 시간과 되돌아간 횟수(승인 뒤 `spec.md`·`plan.md`를 고친 횟수, 테스트가 처음에 통과했는지)를 `STATUS.md`에 한 줄로 남긴다. 다음 주기에 어느 단계를 더 꼼꼼히 할지 정하는 근거다.

## 작은 변경

버그 수정이나 문구 수정처럼 의도와 요구사항이 바뀌지 않는 변경은 Plan과 Design을 건너뛴다.

1. 무엇을 왜 바꾸는지와 바뀌는 파일을 사용자에게 말하고 승인받는다. `plan.md`를 새로 쓰지 않는다.
2. 실패하는 테스트를 먼저 쓰고 고친다.
3. Test의 확인 명령과 Deploy의 검토·승인 절차는 그대로 따른다.
4. `STATUS.md`의 알려진 문제와 배포된 것을 갱신한다.

다음 중 하나라도 해당하면 작은 변경이 아니다: 요구사항(R 번호)이 바뀐다, DB 스키마가 바뀐다, 새 외부 서비스나 권한이 필요하다, 화면 구조나 공개 인터페이스(API, CLI)가 바뀐다.
